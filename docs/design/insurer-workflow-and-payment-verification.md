# 보험사 업무 흐름과 결제 추가 검증

## 기준과 범위

이 프로젝트는 공개 안내를 참고한 보험 업무 시뮬레이터다. 실제 보험사의 요율표·인수 지침·실제 계약 심사나 보험금 송금을 구현했다고 표현하지 않는다.

2026-11-03 확인한 공식 자료:

- [한화생명 다이렉트 가입 안내](https://direct.hanwhalife.com/app/guidance): 상품 설계, 고지사항을 포함한 청약서 작성, 전자서명과 보험료 결제, 이후 심사에 따른 계약 성립 결정을 안내한다. 결제와 계약 성립을 같은 상태로 취급하지 않는 근거다. 모든 보험사의 처리 순서가 같다는 뜻은 아니다.
- [처브라이프 FAQ](https://www.chubblife.co.kr/front/ctmcenter/faq/list.do): 감액·특약 해지와 중도부가를 구분하며, 일부 특약의 중도부가도 회사의 한도·인수 기준을 전제로 안내한다. 보장 추가를 제한 없는 상품 조립으로 일반화하지 않는다.

기존 가입 모형은 `설계·견적 → 고지·약관 동의 → 인수심사 → 승인 후 초회 보험료 → 계약 발행`이다. 이는 현재 구현의 한 가지 모의 순서다. 실제 서비스 연결 시 상품별 청약·수납·승낙 시점을 별도 업무 규칙으로 확정해야 한다.

## 보장 변경

고객이 신청한 것만으로 보장과 보험료가 바뀌지 않도록 다음 경계를 둔다.

1. 고객은 견적과 약관에 동의하고 변경을 신청한다. 유효한 견적을 고정하고 `PENDING_REVIEW`로 저장한다.
2. 심사 대기 동안 기존 계약 버전과 보장·보험료를 유지한다. 동일 신청은 멱등하게 반환한다.
3. 별도 운영자가 중도 변경 조건을 검토하고 사유를 기록하여 승인 또는 반려한다. 고객의 임의 승인과 자기 신청 심사를 차단한다.
4. 승인에 성공한 경우에만 새 계약 버전을 생성한다. 심사 결과·적용 예약·감사 이벤트는 한 트랜잭션이다.
5. 반려·기한 만료 시 기존 계약을 유지한다. 승인 적용에 실패하면 심사 결과도 함께 롤백한다.
6. 승인된 변경은 신청에 고정한 다음 달 1일 서울 0시부터 적용한다. 해당 시각 이후의 늦은 승인은 소급 적용하지 않는다.

다음 달 적용일은 이 모의 상품의 규칙이며 실제 모든 보험상품의 변경일이 아니다. 추가 보장은 면책기간을 확인하고 유지하는 보장의 개시일·지급 이력을 보존한다. 새 보험료는 해당 월에 유효한 계약 버전에서 산정한다. 기존 절차에서 이미 예약한 변경은 `LEGACY`로 구분하며 운영자가 승인했다고 소급 기록하지 않는다.

- 고객 신청/조회: `/api/v1/policies/{policyId}/coverage-changes`
- 운영자 대기 목록: `/api/v1/ops/policy-changes`
- 운영자 판단: `/api/v1/ops/policy-changes/{requestId}/decisions`
- 변경 심사 중에는 고객의 다음 달 선청구를 막는다. 기존 정기 청구는 해당 청구월의 기존 계약을 기준으로 계속 처리한다.

## 알림 순서 역전

- 승인 완료 후 다른 이벤트 ID의 `UNKNOWN`·`FAILED` 알림이 와도 결제·시도·계약 상태를 되돌리지 않는다.
- 먼저 읽어 둔 `UNKNOWN` 조회 응답이 승인 알림 이후 도착해도 승인 상태와 계약 활성화 이벤트를 보존한다.
- 서로 모순되는 최종 결과는 임의로 덮어쓰지 않고 실패 inbox에 남긴다. 자동 정정이나 환불 업무를 구현했다는 뜻은 아니다.
- Toss 일반결제 알림은 payload 상태로 확정하지 않고 기존 거래의 조회 경로를 사용한다. 이미 확정한 초회 승인은 반복 전이시키지 않는다.

이 검증은 초회 승인·계약 활성화 범위다. 결제 취소·환불·차지백은 별도 원장과 업무 규칙이 필요한 별도 범위다.

## PG 지연과 용량 제한

기존 회로 차단은 실패 응답을 받은 뒤 작동하므로, 실패가 쌓이기 전의 동시 요청 묶음은 모두 외부 I/O를 점유할 수 있었다.

- 프로세스 내 PG 동시 호출 수를 `payment.max-concurrent-calls`로 제한한다. 기본값은 16이며 실제 worker 수·다중 인스턴스 수를 고려해 조정해야 한다.
- 승인과 조회가 같은 용량을 공유한다. 용량 확보를 기다리며 worker를 붙잡지 않는다.
- 결제 승인 API는 승인 시도 저장 전에 용량을 확보한다. 전송 전 용량 부족은 HTTP 503으로 안내하고 주문을 `CREATED`로 유지한다. 같은 주문·키로 다시 요청할 수 있다.
- 이미 진행한 거래의 조회가 용량 부족이면 `UNKNOWN`을 유지하고 기존 대사 경로로 넘긴다.
- 용량 부족을 PG의 장애 횟수로 누적하지 않는다. 성공·예외 경로에서 용량을 반환한다.

## 측정 방법

`paymentLatencyMeasurement`는 명시적으로 실행하는 실험이며 기본 테스트에서 제외한다.

- 애플리케이션 worker를 모형화한 고정 실행 슬롯 8개와 결제 작업 8개, 정상 작업 20개를 사용한다.
- 런타임에 만든 인증서로 로컬 HTTPS PG를 실행한다. 실제 JDK HttpClient 요청의 2초 timeout을 확인한다. 실제 Toss endpoint로 접속하지 않는다.
- 변경 전과 PG 슬롯 2개를 적용한 변경 후 각각 3회 측정한다.
- 기록하는 값은 정상 작업의 실행 대기 시간 p50/p95, 실제 PG 동시 호출 수, timeout·용량 거절 수다.
- DB·전문 저장 비용과 실제 운영 API 서버는 이 지연 실험에서 제외한다. 결과를 운영 TPS·API 응답시간·SLA로 표현하지 않는다.
- PostgreSQL 기반 결제·계약·심사 통합 시험은 별도로 수행한다.


## 재현 명령

Java 21과 로컬 Docker가 필요하다. 실제 Toss 자격 증명은 사용하지 않는다.

```bash
cd Backend
./gradlew test --tests 'com.capsule.insurance.payment.*' --tests 'com.capsule.insurance.migration.*'
./gradlew paymentLatencyMeasurement -PpaymentLatencyCapacity=8 -PpaymentLatencyOutput=build/payment-latency-capacity-8.json
./gradlew paymentLatencyMeasurement -PpaymentLatencyCapacity=2 -PpaymentLatencyOutput=build/payment-latency-capacity-2.json
```

첫 번째 용량 실험은 worker와 PG 용량이 모두 8인 경우를, 두 번째는 PG 용량 2로 여유 worker를 남기는 경우를 재현한다. 원래 코드에서 측정한 수정 전 기준선도 로컬 검증 기록에 보존했다. 실험은 실행 환경의 스케줄링 영향을 받으며 작은 대기 시간 수치를 서비스 전체 성능으로 일반화하지 않는다.
