# 선택 보장 및 다음 달 변경 — 모의 보험 규칙

이 기능은 `CAPSURE-DEMO-CANCER`에만 설정된 교육용 보험료를 사용한다. 공개 보험 상품의 실제 요율이나 인수 정책이 아니다. 기존 상품 묶음 구독 `/subscriptions`는 변경하지 않는다.

## 사용자 흐름

1. 상품 화면에서 보장을 선택한다. 일반암 19,900원, 유사암 7,000원, 수술 3,000원의 합계가 예상 보험료다.
2. 서버가 선택 ID의 상품 소속·중복·요율을 검증하고 합계를 견적 스냅샷에 저장한다. 클라이언트가 금액을 정하지 않는다.
3. 청약·결제는 저장된 견적 금액을 사용한다. 계약에는 선택 보장과 보장별 보험료를 함께 보존한다.
4. 가입 후 증권 화면에서 변경할 보장을 선택하고 새 견적과 약관에 동의한다.
5. 다음 달 1일 00:00 Asia/Seoul부터 적용할 계약 버전을 같은 트랜잭션에서 예약한다.
6. 다음 달 납부 내역 생성은 해당 청구일에 유효한 버전의 보험료를 사용하고 `policy_version_id`를 남긴다.

## 시점 및 불변식

- 계약 버전 구간은 `[valid_from, valid_to)`다. 적용 전에는 기존 버전, 경계부터는 새 버전을 조회한다. 배치가 제때 실행되어야만 변경되는 구조가 아니다.
- 보장 추가는 적용일에서 면책일수를 더한다. 계속 유지하는 보장은 기존 보장개시일·심사 규칙을 보존한다.
- 이전 사고 심사에서는 당시 버전의 종료일과 계약 실효일을 함께 고려한다. 미래 버전의 보장을 과거 사고에 소급하지 않는다.
- 최초 진단 지급 횟수는 동일 계약·상품 보장의 모든 버전을 합산한다. 버전 변경으로 지급 제한이 초기화되지 않는다.
- 정책 행 잠금으로 예약·다음 달 청구 생성을 직렬화한다. 다음 달 청구가 이미 있으면 보장 변경을 거절한다.
- 정상 유지 계약만 변경 가능하다. 한 계약의 같은 적용일에는 한 예약만 허용한다.
- 같은 키·같은 견적·같은 동의는 기존 결과를 반환한다. 다른 내용은 충돌로 거절한다.
- 변경 예약, 기존 구간 종료, 새 버전·보장 생성, 견적 사용 처리, 변경 이벤트 기록은 한 DB 트랜잭션이다.

## API

- `POST /api/v1/policies/{id}/coverage-changes`: `Idempotency-Key`, `{quoteId, documentHash, agreed}`
- `GET /api/v1/policies/{id}/coverage-changes`: 소유자에게 예약·적용 내역 반환
- `POST /api/v1/policies/{id}/next-premium`: 서버에서 다음 달 청구 금액·청구일 산정. 같은 월 재호출은 기존 청구 반환

보험료 부분 납부·실효·부활 규칙은 기존 모의 보험료 수납 모듈을 따른다. 변경 예약은 실효 계약을 활성화하지 않는다. 기존에 확정된 견적·계약은 최신 상품 보험료 변경에 따라 다시 계산하지 않는다.

## 검증

- 결제 확인 재요청 10개 + 동일 PG 알림 10개 + 대사 10개 경합: 기존 승인 1회, 계약 활성화 이벤트 1개.
- 별도 JVM에서 모의 PG 원장 승인 기록을 독립 커밋한 직후 프로세스를 강제 종료한다. 새로운 JVM이 원장을 조회해 재승인 없이 계약을 복구한다. PG 원장은 테스트용 별도 테이블이며 실제 외부 PG 장애 시험이 아니다.
- 단일·복수 보장 요율, 선택 보장의 결제·계약 반영, 변경 직전·정각의 버전, 추가 담보 면책, 기존 담보 개시일 유지, 청구 금액·버전 연결, 만료·미동의·중복 예약·권한 검증을 시험한다.

## 현재 범위

- 같은 모의 상품 안에서만 변경한다. 보장금액 직접 조절, 상품 간 전환, 예약 취소·교체, 실제 보험사 재심사는 포함하지 않는다.
- 다음 달 청구 생성은 모의 화면의 명시적 동작이다. 실제 정기 결제·청구 배포나 외부 PG 연결을 의미하지 않는다.
- 기존 계약의 과거 스냅샷에는 보장별 보험료가 없을 수 있다. 확정 월 보험료는 기존 값을 유지한다.
