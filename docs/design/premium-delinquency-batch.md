# 보험료 미납 배치와 계약 효력 — 가상 상품 규칙

## 목적과 범위

단일 출금 실패 대신 확정 수납액·미수액·모의 독촉·유예 종료일로 계약 상태를 판정한다. 기존 수납 및 환급 원장을 보존한다. 실제 보험 약관이나 법규 준수를 보증하지 않는다. 실제 메시지 발송, PG 출금, 자동 부활, 정기 채권 생성 및 배포는 포함하지 않는다.

## 상태와 날짜

- 업무일은 `Asia/Seoul`, 납부기일/유예 종료일은 당일까지 유효하다.
- 납부기일 다음 날 미수액이 있으면 `GRACE`. 출금 실패 상태만으로는 변경하지 않는다.
- 모의 독촉은 `SIMULATED_DELIVERED` 또는 `FAILED`. 실제 전달을 의미하지 않는다.
- 최초 모의 독촉 성공일 + 설정된 최소 유예일과 기존 `grace_ends_on` 중 늦은 날을 적용 기한으로 고정한다.
- 가상 정책 `SIMULATED-V1`, 기본 최소 유예일은 14일이다. 이는 법정 기간을 뜻하지 않는다. 설정값과 적용 기한을 채권별 독촉 원장에 저장한다.
- 독촉 실패만 있는 채권으로는 실효시킬 수 없다. 성공한 다른 연체 채권의 유예 종료는 독립적으로 실효 사유가 될 수 있다.
- 유예 종료 다음 날에도 미수액이 남아 있으면 `LAPSED`. `lapsed_at`은 해당 업무일의 한국시간 자정이다. 배치의 기록 시각은 별도 보존한다.
- 유예 중 모든 연체 회차가 완납되면 `ACTIVE`; 미래 납부 회차는 복귀를 막지 않는다.
- 유예 종료 후 아직 일일 배치가 실행되지 않았더라도 수납 직전 동일한 실효 규칙을 적용한다. 스케줄러 지연이 자동 부활로 이어지지 않도록 한다. 수납 요청이 실패하면 이 상태 전이도 같은 트랜잭션에서 롤백된다.
- 실효 후 수납은 사실대로 기록하되 계약을 부활시키지 않고 `pay_late_settlement_review`에 남긴다. 이미 실효된 계약은 배치가 다시 변경하지 않는다.
- 현재 확정된 수납 잔액을 기준으로 판단한다. 지연 수납의 실제 은행 거래일 소급 정정 및 부활 심사는 별도 범위다.

## 동시성·재시작

- 계약 → 채권 → 출금 지시 순서로 모든 수납 경로와 배치가 잠금을 획득한다. 다른 계약은 병렬 처리할 수 있다.
- 실행 키는 유일하며 실행 시점의 대상 계약 목록을 고정한다. 동일 키를 다시 보내면 같은 실행을 재개/조회한다. 새로 생성된 채권은 새 실행에서 점검한다.
- 20개 계약 단위로 상태 변경·독촉·결과 체크포인트를 함께 커밋한다. 장애가 난 chunk는 전부 롤백하고 미처리 대상부터 재개한다.
- 실행 행의 `FOR UPDATE SKIP LOCKED`는 같은 실행을 두 작업자가 동시에 처리하지 못하게 한다. 다른 실행 사이의 중복은 계약 잠금과 채권당 하나의 독촉 원장으로 방지한다.
- 대상 목록의 처리 여부를 사용하므로 경쟁 선점된 낮은 ID가 high-water mark 아래로 빠져 누락되지 않는다.
- `대상 = 처리 + 남음`, `처리 = 변경 + 유지 + 독촉 실패`. 독촉 실패는 그 실행에서 처리된 결과이며 새 실행에서 재시도한다. 시스템 예외는 `FAILED` 실행으로 남고 같은 실행을 재개한다.
- 모의 gateway는 트랜잭션 안에서 동작한다. 실제 외부 발송 adapter로 교체할 때는 Outbox 및 전달 확인 흐름을 별도 설계해야 한다.

## 수납·청구 연동

- 부분 납부를 `SETTLED`로 오인하지 않는다. 완납 전 자동출금 지시는 취소하지 않는다.
- 동일 수납 키 재전송은 한 건으로 유지하며 키의 다른 금액/채권 재사용은 거부한다.
- 미확정 `SUBMITTED`, `CANCEL_REQUESTED`, `UNKNOWN` 지시는 실효 이후에도 보존하며 결과 수신이 가능하다.
- 유예 중 청구를 허용한다. 실효 전 사고의 사후 청구는 허용하되 실효 시점 이상인 사고는 제외한다. 기존 초안의 지급심사와 지급 직전에도 보장 종료일과 실효 시점을 함께 반영한다.

## 운영 API와 화면

모든 경로는 기존 `/api/v1/ops/**` 관리자 RBAC를 적용한다.

- `POST /api/v1/ops/premium-collections/delinquency/runs`: `{instanceKey, reason}`. 업무일은 서버 결정.
- `GET .../runs`: 최근 8개 실행.
- `GET .../runs/{id}`: 결과와 control total.
- `POST .../runs/{id}/resume`: `{reason}`. 최초 실행과 재개 요청자의 ID·사유를 별도 기록.
- 기존 수납 타임라인에 계약 상태, 납부기일, 적용 유예 종료일, 모의 독촉 상태, 최근 변경 사유, 실효 시점, 실효 후 수납 검토 건수 추가.
- 화면은 실행 실패/미확정 응답 시 동일 요청 키를 재사용하며, 실패한 실행은 동일 ID로 재개한다.

## 실행 설정

`operations.premium-delinquency.scheduler-enabled`는 기본 false. 명시적으로 true일 때만 매일 한국시간 00:10 실행한다. `cron`과 `simulated-grace-days`는 같은 prefix의 설정으로 바꿀 수 있다. 자동 실행 실패가 있으면 운영 화면에서 같은 실행을 재개한다.

## 검증

`PremiumDelinquencyIntegrationTest`, `PremiumDelinquencySecurityTest`, `ClaimAssessmentIntegrationTest`에서 날짜 경계, 독촉 실패, 지연 독촉, 다회차/부분 납부, 실효 후 미확정 출금 확정, 멱등 수납, 100건 동시 실행, 같은 실행 경쟁, chunk 실패 복구, 청구 시점, 관리자 권한을 검증한다. 측정 결과·환경·스크린샷은 Git 제외 `docs/evidence/`에 보관한다.
